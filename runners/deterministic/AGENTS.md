# IEF Deterministic Runner Stub Contract Spec

> Stage D P0 -- Deterministic stub only. No multi-runner orchestration. No external tool integrations. No runner self-approval.

| Runner Type | Scope |

## Phase 1.1: Stub Runner Definition

The deterministic stub is a single runner implementation that:

- Accepts a `TaskEnvelope` from the Operations coordination plane.
- Validates the envelope against the Protocol schema.
- Checks the dedupe key against a local execution cache.
- **Does NOT dispatch to any external tool or process.**
- Emits a controlled sequence of `RunEvent` objects simulating a minimal lifecycle.
- Records partial or zero `ArtifactRef` objects (stub evidence only).
- Cannot self-approve or mark its own work as accepted.

### Interface Contract

```
interface DeterministicStubRunner {
  id: "deterministic-stub"
  
  // Core lifecycle
  accept(envelope: TaskEnvelope): Promise<RunEvent>    // validation + dedupe check
  execute(envelope: TaskEnvelope): Promise<RunEvent>   // deterministic stub "execution"
  report(): Promise<RunEvent[]>                        // return all events for this run
  
  // Cache operations
  cache_lookup(dedupe_key: string): CachedResult | null
  cache_store(dedupe_key: string, events: RunEvent[], artifacts: ArtifactRef[]): void
}
```

### Input Requirements

- `TaskEnvelope` must conform to the IEF Protocol schema.
- `TaskEnvelope.dedupe_key` must be a non-empty string.
- `TaskEnvelope.intent` must be `"directive"`.
- Missing or malformed fields -> reject with `schema_validation_failed`.

## Phase 1.2: Stub Lifecycle -- Deterministic State Transitions

The stub emits exactly these events for every envelope, in order:

| Step | RunEvent Status | Condition |
|---|---|---|
| 1 | `started` | Envelope received, validation passed, dedupe key not seen |
| 2 | `completed` | Stub execution "done" (deterministic: immediate, no work performed) |

### Error Branches

If validation fails at step 1:
- Emit `failed` with `error_code: "schema_validation_failed"`.
- Do NOT proceed to step 2.

If dedupe key is already in cache:
- Emit `failed` with `error_code: "dedupe_duplicate"`.
- Return cached `RunEvent[]` and `ArtifactRef[]` without re-execution.

If envelope state is `stop_requested`, `cancelled`, or `locked`:
- Do NOT emit `started`.
- Emit `stopped`, `cancelled`, or `locked` respectively.

### State Transition Diagram

```
TaskEnvelope received
  |
  v
[Validate] --fail--> RunEvent(status=failed, error_code=schema_validation_failed)
  |
  pass
  v
[Check dedupe] --duplicate--> RunEvent(status=failed, error_code=dedupe_duplicate) + cached result
  |
  new
  v
[Check envelope state]
  |-- stop_requested --> RunEvent(status=stopped)
  |-- cancelled      --> RunEvent(status=cancelled)
  |-- locked         --> RunEvent(status=locked)
  |-- normal         |
  v
RunEvent(status=started)
  |
  v
[deterministic no-op execution]
  |
  v
RunEvent(status=completed) + optional ArtifactRef(stub_evidence)
```

## Phase 1.3: RunEvent Schema (Stub)

Every `RunEvent` produced by the stub:

```
RunEvent {
  event_id: <UUID>
  envelope_id: <TaskEnvelope.envelope_id>
  runner_id: "deterministic-stub"
  status: "started" | "completed" | "failed" | "stopped" | "cancelled" | "locked" | "timed_out"
  tool_runner_type: "deterministic_stub"
  started_at: <ISO-8601 UTC | null>
  finished_at: <ISO-8601 UTC | null>
  exit_code: <number | null>
  error_code: <string | null>
  error_message: <string | null>
  artifact_refs: <ArtifactRef[]>
  evidence_summary: <string | null>
  reason: <string | null>
  elapsed_ms: <number | null>
}
```

### Field Rules

| Field | Rule |
|---|---|
| `event_id` | UUID v4, generated by runner, unique per event |
| `envelope_id` | Must match the source `TaskEnvelope.envelope_id` |
| `runner_id` | Always `"deterministic-stub"` |
| `status` | One of the enumerated values; see Phase 1.2 for transition rules |
| `tool_runner_type` | Always `"deterministic_stub"` |
| `started_at` | Set when status=`started`; null otherwise |
| `finished_at` | Set when status is `completed`, `failed`, `stopped`, `cancelled`, `locked`, or `timed_out` |
| `exit_code` | `0` for `completed`; non-zero for `failed`; null for other states |
| `error_code` | `"schema_validation_failed"` or `"dedupe_duplicate"` for `failed`; null otherwise |
| `error_message` | Human-readable error detail for `failed`; null otherwise |
| `artifact_refs` | Zero or one `ArtifactRef` (see Phase 1.4) |
| `evidence_summary` | Short text summary for `completed` runs; null otherwise |
| `reason` | Explanation for `stopped`/`cancelled`/`locked` states; null otherwise |
| `elapsed_ms` | Time from `started_at` to `finished_at` in milliseconds; null if not applicable |

### Stub-Specific Behavior

- `elapsed_ms` will always be near-zero (deterministic no-op).
- `exit_code` is `0` for all `completed` events (stub never "fails" during execution).
- `evidence_summary` for completed runs: `"Deterministic stub: envelope accepted, no work performed, run recorded."`

## Phase 1.4: ArtifactRef Schema (Stub)

Stub may emit zero or one deterministic `ArtifactRef`:

```
ArtifactRef {
  artifact_id: <UUID>
  envelope_id: <TaskEnvelope.envelope_id>
  type: "stub_evidence"
  name: "deterministic-run-report"
  content_type: "application/json"
  content: <JSON object>
  created_at: <ISO-8601 UTC>
}
```

### Content Object

```json
{
  "envelope_id": "<TaskEnvelope.envelope_id>",
  "runner_id": "deterministic-stub",
  "status": "completed",
  "started_at": "<ISO-8601 UTC>",
  "finished_at": "<ISO-8601 UTC>",
  "dedupe_key": "<TaskEnvelope.dedupe_key>"
}
```

### Artifact Rules

- Emitted only when run reaches `completed` status.
- Not emitted for `failed`, `stopped`, `cancelled`, or `locked` runs.
- `artifact_id` is UUID v4, unique per artifact.
- `type` is always `"stub_evidence"`.

## Phase 1.5: Self-Approval Prohibition (Hard Boundary)

> **This is a non-negotiable Stage D boundary.**

- The stub runner **MUST NOT** mark any task as accepted, merged, closed, or approved.
- The stub runner **MUST NOT** decide that its own output is sufficient for downstream consumption.
- All `RunEvent` status values are **reports to Operations**, not decisions.
- Only an external review gate (Operations or human) may accept or reject stub output.

### Prohibition Rules

| Action | Allowed? |
|---|---|
| Emit `RunEvent` with status `completed` | Yes (report only) |
| Set `exit_code` to `0` | Yes (report only) |
| Emit `ArtifactRef` with stub evidence | Yes (report only) |
| Mark envelope as "accepted" | **NO** |
| Mark envelope as "approved" | **NO** |
| Trigger downstream merge/close | **NO** |
| Decide own output quality | **NO** |
| Modify own cache to hide failures | **NO** |
| Re-emit events to override prior status | **NO** |

### Rationale

The deterministic stub is a test/validation tool. It produces structured evidence that Operations can inspect. The stub has zero authority to judge its own output. This separation ensures that:

1. No automated process can self-certify completion.
2. All acceptance decisions flow through the Operations coordination plane or a human reviewer.
3. The audit trail (RunEvent + ArtifactRef) is a faithful record, not a self-serving claim.

## Phase 1.6: Dedupe and Idempotency

- Same dedupe key -> do NOT re-emit RunEvents. Return cached result.
- Cache stores: `dedupe_key -> [RunEvent[], ArtifactRef[]]`.
- Cache is append-only: new events are added, old events are never deleted.
- On restart: cache is reloaded; previously processed envelopes produce no new events.

### Cache Schema

```
ExecutionCache {
  entries: Map<string, CachedResult>
}

CachedResult {
  dedupe_key: <string>
  events: RunEvent[]
  artifacts: ArtifactRef[]
  cached_at: <ISO-8601 UTC>
}
```

### Idempotency Guarantees

1. **Exactly-once semantics per dedupe key**: First invocation produces events; subsequent invocations return cached result with no new side effects.
2. **Append-only cache**: Entries are never overwritten or deleted. This preserves the full audit trail.
3. **Restart safety**: Cache is persisted before emitting the `completed` event. A crash before persist means the next run will re-execute (producing identical output due to determinism).
4. **No partial writes**: Either the full `[RunEvent[], ArtifactRef[]]` tuple is cached, or nothing is cached.

### Cache Operations

```
// On envelope receipt:
function process(envelope: TaskEnvelope):
  key = envelope.dedupe_key
  
  // Check cache
  cached = cache.lookup(key)
  if cached != null:
    return cached.events   // idempotent replay
  
  // Validate
  validation = validate(envelope)
  if !validation.ok:
    return [RunEvent(status=failed, error_code=schema_validation_failed)]
  
  // Execute (deterministic no-op)
  started = RunEvent(status=started, started_at=now())
  completed = RunEvent(status=completed, finished_at=now(), exit_code=0)
  
  // Persist to cache BEFORE returning
  cache.store(key, [started, completed], artifacts)
  
  return [started, completed]
```

## Implementation Notes

### File Structure

```
runners/deterministic/
  AGENTS.md    -- this contract spec
  init.sh      -- bootstrap stub
```

### Relationship to Other Runners

| Runner | Status | Relationship |
|---|---|---|
| `claudecode` | Active (runners/claudecode/) | Independent; no coupling with deterministic stub |
| `deterministic-stub` | Contract spec only | Standalone; no shared code paths |

The deterministic stub does NOT orchestrate, coordinate with, or dispatch to any other runner. It is a self-contained validation tool.

### Control Character Policy

All text fields in `RunEvent` and `ArtifactRef` must be normalized:
- No Unicode control characters (U+0000-U+001F except tab/newline, U+007F-U+009F).
- No BOM (byte order mark).
- No smart quotes or typographic substitutions.
- Plain ASCII for structural fields; UTF-8 allowed in `evidence_summary` and `error_message` only after control character stripping.
